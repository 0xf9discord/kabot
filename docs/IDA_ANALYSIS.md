# IDA Pro 9.3 정적 분석 기록

분석일: 2026-10-31 (Asia/Seoul). **1·2차 정적 분석 단계에서는** 카카오톡을
실행하지 않고 설치된 실행 파일을 작업 폴더로 복사해 IDA 데이터베이스를 만들었다.
분석 도구로 계정 데이터, 토큰, 사용자 메시지 데이터베이스를 읽지 않았다.
뒤의 **3차 단계에서는 원본 앱을 숨김 실행했으나 연결 전에 종료되었다**.
**4차 단계에서는 별도로 x86 원본 앱의 제한된 실행 코드 구간을 관찰·복원했다**.
앱 자체의 초기화 중 파일/네트워크 동작은 관찰하지 않았으므로 그 부재를 주장하지 않는다.

## 사용한 도구와 근거의 구분

- 실제로 실행한 엔진: `C:\Program Files\IDA Professional 9.3\idalib.dll`.
- `idapro.get_library_version()` 결과: **9.3.260213**.
- 사용자 프로필의 전역 MCP 설정을 변경하지 않고, 자식 프로세스의 `IDADIR`과
  `PYTHONPATH`로 기존 IDA 라이브러리를 지정했다.
- 이 문서와 `analysis/`의 JSON은 **로컬 IDAPython 관찰 결과**다.
  REA가 발급한 Evidence ID로 표현하지 않는다.
- 앞서 REA의 PE import 분석은 수행되었고 `rea-evidence.json`에 별도 보관했다.
  REA의 심층 분석 경로는 `REA_IDA_MCP_CONFIG` 미설정으로 사용할 수 없었으므로
  IDA의 공식 번들 idalib/IDAPython으로 후속 관찰했다.

정확한 보호 제품 버전이나 모든 계층을 식별한 결과는 아니다.

`analysis/kakao-26.8-x64/report.json`은 전체 관찰값,
`analysis/kakao-26.8-x64/entrypoint.json`은 두 함수의 경계, 엔트리포인트의
최대 80개 명령과 생성된 의사코드를 담는다.

## 아직 확인되지 않은 것

- 개인 계정 인증 요청 형식, 기기 등록, 서버가 요구하는 현재 검증 단계.
- LOCO 프레임 구조, 암호화/키 협상, 로그인 이후의 세션 상태 전이.
- 일반 단체방 메시지 수신, 쓰기, 재접속의 실제 동작.
- 실행 중 풀리는 코드와 위 기능들의 호출 관계.

따라서 이 분석만을 근거로 카카오톡 설치 없는 개인 계정/단체방 독립 클라이언트가
완성되었다고 주장할 수 없다. 공식 메시지 REST API의 개인 계정 발송 기능은
이 비공개 단체방 클라이언트 기능과 구별해서 제공해야 한다.

후속 분석에 필요한 증거는 보호 계층 뒤의 실제 코드 또는 계정 소유자가 제공하는
통제된 실행/통신 관찰이다. 이번 단계에서 이를 관찰하지 않았으며 인증 우회나
토큰 추출을 구현하지 않았다.

## 재현

Windows PowerShell에서 프로젝트 루트를 작업 경로로 사용한다. 출력 디렉터리는
기존 결과를 덮어쓰지 않도록 **새 이름**을 지정해야 한다.

```powershell
$env:IDADIR = 'C:\Program Files\IDA Professional 9.3'
$env:PYTHONPATH = 'C:\Program Files\IDA Professional 9.3\idalib\python'
python tools\ida_static_probe.py `
  'C:\Program Files\Kakao\KakaoTalk\KakaoTalk.exe' `
  docs\analysis\new-x64-probe --analyze
python tools\ida_inspect_database.py `
  docs\analysis\new-x64-probe\KakaoTalk.exe.i64 `
  docs\analysis\new-x64-probe\entrypoint.json --decompile
```

설치된 IDA에 포함된 `idalib/README.txt`, `idalib/python/idapro/__init__.py`,
`idalib/python/idapro/config.py`의 실제 API와 환경 변수 동작을 확인해 사용했다.
설치본의 실행 파일/라이선스/설정은 수정하지 않았다. 복사된 카카오톡 실행 파일과
IDA 데이터베이스는 로컬 분석용이며 `.gitignore`로 배포 대상에서 제외한다.

## 2차 분석: 첫 번째 압축 계층의 오프라인 복원

추가 요청에 따라 같은 IDA 9.3 데이터베이스에서 로더의 보조 함수를 조사했다.
실제 카카오톡 프로세스를 시작하거나 네이티브 코드를 호스트에서 실행하지 않고,
입력 바이트를 순수 Python의 제한된 압축 해제 함수로 해석했다.

### IDA에서 직접 관찰한 입출력 위치

`sub_1447E01DF`의 디스어셈블리를 기준으로 다음 값을 계산했다.

- `start`의 반환 주소 `0x1447e005d`에서 `5`와 `0x13ec058`을 빼면
  출력 시작 주소 **`0x1433f4000`**이다 (`.themida`의 시작).
- 반환 주소에 `0x1f0 - 5`를 더하면 압축 데이터 위치 **`0x1447e0248`**이다.
- 이 위치의 첫 바이트를 스트림 개수로 사용하고, 각 스트림을 해제하면서
  입력 포인터와 출력 포인터를 전진시킨다.
- 마지막에 출력 시작 주소에 `0x382b5d`를 더한 **`0x143776b5d`**로 이동한다.

원래 IDA 출력은 `analysis/phase2-x64/loader-functions.json`에 저장했다.
해당 함수의 LZ 비트 플래그, 리터럴, 이전 출력에 대한 역참조를 해석하는
`tools/static_unpack.py`를 작성했다. 잘못된 참조, 잘린 입력, 과도한 출력 및
심볼 수, 처리 시간 초과는 오류로 처리한다.

### 복원 결과

| 압축 스트림 수 | 32개 |
| 복원한 바이트 수 | 20,889,600 (`0x13ec000`) |
| 원래 `.themida` 가상 크기와 비교 | 정확히 일치 |
| 복원 구간 SHA-256 | `54197ba1714aa19e948c995e615203178ff7dac58ab9edc7faef1903e0a8c38c` |
| 분석용 PE SHA-256 | `c0e7bca85335095d6d63e8bf339cb824eb698a5b67ae5ee079956fd2f9d8d146` |
| IDA 9.3 재분석 시간 | 77.92초, 자동 분석 완료 |

오프라인 복원은 성공했다. 결과는
`analysis/phase2-x64/decoded/report.json`과
`analysis/phase2-x64/ida-stage1/report.json`에 기록했다.
원본 PE의 한 구간을 복원 데이터로 교체하고 새 진입점을 지정한 이미지는
**IDA 분석용**이다. 설치된 파일을 교체하지 않았고 이 이미지를 실행하지 않았다.

7개의 독립적인 소형 압축 스트림으로 리터럴, 겹치는 짧은/긴 역참조,
이전 오프셋 재사용, 0 바이트, 잘린 입력, 잘못된 참조, 자원 제한을 검증했다.
`python tools/test_static_unpack.py`가 모두 통과했다.
전체 실제 데이터에 대해서도 32개 스트림 모두 정상 종료했으며 위 크기를 복원했다.

### 복원된 것이 실제 채팅 코드인가?

현재 근거로는 **다음 보호 계층**이라는 해석이 더 타당하다.
동일한 후보 패턴 검색은 카카오 로그인/LOCO 코드 대신
`CheckIN`, `CheckOUT`, `ProcIN`, `ExitIN` 등을 출력하는 보호 계층의
진단 문자열 한 개를 찾았다. 이것을 카카오 서버의 `CHECKIN` 명령으로
해석할 근거는 없다.

추가로 다음 직접 분기/호출을 추적하고 Hex-Rays 의사코드도 저장했다.

```text
start 0x143776b5d
  -> 0x1436bf919
  -> 0x143416c48
  -> 0x1438418dc
  -> 0x143b13f3a
  -> jmp qword ptr [rax] (0x143b14c84)
```

관련 출력은 `analysis/phase2-x64/ida-stage1/entrypoint.json`과
`next-functions*.json`이다. 마지막 함수는 난독화된 문맥/테이블을 조작하고
계산된 주소로 간접 분기한다. 가상화된 디스패치라는 **추론**에 부합하지만,
핸들러의 의미와 이후 제어 흐름 전체를 복원한 것은 아니다. 일부 의사코드에는
스택 추적 경고도 있으므로 변수 이름이나 추정된 인자 형식을 규격으로 쓰면 안 된다.

따라서 첫 계층을 실제로 복원한 진전은 있으나, 인증/키 협상/채팅 전송 코드는
아직 확인되지 않았다. 이 상태에서 동작하는 개인 계정/단체방 독립 접속을
구현했다고 표시할 수 없다. 다음 단계에는 간접 디스패처의 의미 복원 또는
통제된 실제 실행 관찰이 필요하다. 2차 단계에서는 후자를 수행하지 않았다.

### 2차 분석 재현

앞서 제시한 `IDADIR`, `PYTHONPATH` 설정을 그대로 사용한다.

```powershell
python tools\ida_dump_functions.py `
  docs\analysis\kakao-26.8-x64\KakaoTalk.exe.i64 `
  docs\analysis\phase2-new\loader-functions.json `
  0x1447e0058 0x1447e01df
python tools\static_unpack.py `
  docs\analysis\kakao-26.8-x64\KakaoTalk.exe `
  docs\analysis\phase2-new\decoded `
  --source-va 0x1447e0248 --target-va 0x1433f4000 --next-va 0x143776b5d `
  --expected-sha256 f94e569ea674059d526314f50d79c32bd3e05c30be90f4c51269703b70a71b9c
python tools\ida_static_probe.py `
  docs\analysis\phase2-new\decoded\stage1-analysis.exe `
  docs\analysis\phase2-new\ida-stage1 --analyze
python tools\test_static_unpack.py
```

출력 디렉터리를 새로 지정해야 하며, 주소 상수는 위 SHA-256의 x64 대상에만
근거가 있다. 다른 버전에 이 값을 그대로 적용해서는 안 된다.

## 3차 분석: 30초 한도의 숨김 실행과 메타데이터 관찰 시도

정적 분석에 이어 원본 x64 설치본을 대상으로 **한 번** 실행/연결을 시도했다.
대상은 `C:\Program Files\Kakao\KakaoTalk\KakaoTalk.exe`이며,
실행 직전 SHA-256이 앞서 분석한 `f94e569e...70a71b9c`와 일치함을 확인했다.
실행 전 이름으로 확인한 기존 카카오톡 프로세스는 없었다.

`Start-Process -WindowStyle Hidden -PassThru`를 사용했고 추가 인자를 넘기지 않았다.
소유 프로세스의 PID, 경로, 생성 시각을 기록하고 최대 30초 뒤에는 동일한
경로와 생성 시각의 **해당 PID만** 종료하도록 수명 관리 스크립트를 사용했다.

| 항목 | 실제 결과 |
| --- | --- |
| 소유한 PID | 14432 |
| 생성 시각 (Asia/Seoul) | 2026-10-31 20:59:39.3986737 |
| 종료 확인 시각 (Asia/Seoul) | 2026-10-31 20:59:49.2155149 |
| 앱 수명 | 10초 미만, 도구의 강제 종료 전에 자체 종료 |
| 종료 후 카카오톡 프로세스 | 없음 |
| REA Frida 연결 시도 | 1회, 실패 |
| 연결 오류 코드 / 범주 | `capability_unavailable` / `unsupported_provider` |
| 정확한 오류 이유 | `Unable to find process with pid 14432` |
| Frida 세션/스크립트 | 세션 생성 실패, 스크립트 로드 안 함 |

종료 원인과 종료 코드는 관찰하지 못했다. 이 결과만으로 보호 기능에 의한 종료,
계정 상태, 네트워크 실패 등을 원인으로 지목할 수 없다. 앱이 종료되었으므로
동일한 실행/연결을 반복하거나 보호 우회를 시도하지 않았다.

관찰용 스크립트는 주 모듈의 PE 헤더와 섹션/보호 속성 정보만 반환하도록 준비했다.
그러나 **실제로 로드되지 않았으므로 런타임 매핑 정보조차 얻지 못했다**.
실행 코드 바이트 덤프, 메모리 스캔, 힙/스택 읽기, 계정/데이터베이스 후킹,
네트워크 후킹은 수행하지 않았다. 비밀번호 입력, 사용자 GUI 조작,
수동 메시지 발송도 하지 않았다. 일반 앱 초기화 자체의 파일 읽기나 네트워크
접속은 관찰 범위 밖이었고, 없었다고 단정하지 않는다.

### 보관한 기록

- `analysis/phase3-runtime/lifecycle.json`: PowerShell이 관찰한 실행/종료 기록.
  **REA Evidence가 아닌 일반 프로세스 수명 기록**이다.
- `analysis/phase3-runtime/attach-result.json`: 실제 연결 요청과 REA의 전체 오류 응답.
- `analysis/phase3-runtime/evidence.json`: REA Evidence 내보내기를 수행한 결과.
  **레코드 수는 0개**다. 연결 실패 응답이 Evidence 원장에 등록되지 않았으므로
  존재하지 않는 런타임 Evidence ID를 만들거나 연결 성공으로 표현하지 않는다.
- `tools/observe_kakao_lifecycle.ps1`: 소유 PID의 신원을 확인하는 30초 수명 관리 스크립트.
- `tools/kakao_metadata_probe.js`: 준비한 메타데이터 전용 스크립트. 문법 검사만
  통과했고 대상에서 실행되지는 않았다.

연결된 Frida 세션이 없어 닫을 세션도 없었다. 수명 관리 스크립트가 종료와
남은 프로세스 부재를 확인했으며, 후속 이름/부모 PID 목록 확인에서도
카카오톡 프로세스가 없었다. 다른 프로세스를 종료하지 않았다.

이번 시도는 실제 앱 코드의 메모리 복원으로 이어지지 못했다.
현재 제공되는 LOCO 코덱/연결 테스트는 별도 로컬 테스트 서버와의 검증이며,
이 카카오톡 실행이나 실제 서버 로그인 성공을 뜻하지 않는다.

## 4차 분석: x86 실행 코드 구간의 실제 복원과 IDA 9.3 재분석

팀의 별도 런타임 관찰에서 x86 설치본의 **첫 번째 실행 가능 PE 구간만**
캡처했다. 이 절에서는 이미 저장된 스냅샷으로 오프라인 비교와 IDA 분석을 했다.
추가 앱 실행이나 메모리 관찰은 하지 않았다.

### 캡처 범위와 증거 한계

- 설치본: `C:\Program Files (x86)\Kakao\KakaoTalk\KakaoTalk.exe`,
  정적 SHA-256 `86f384d1694c74a611181e6c88509e8f59eb8d9739ae3d7789711a9355757500`.
- 캡처: RVA `0x1000`, 크기 `0x1f1c000` = **32,620,544바이트**.
  PE VirtualSize `0x1f1b2c5`를 페이지 경계로 올린 첫 코드 구간이다.
- 캡처 시 확인한 보호 속성은 정확히 `r-x`였다. 쓰기 가능 구간, 힙/스택,
  익명 메모리, 사용자 데이터베이스는 캡처하지 않았다.
- 관찰된 기본 주소는 `0x400000`으로 원본 PE의 기본 주소와 같았다.
- 별도의 PE 메타데이터 파싱 시도는 일반 `Error`로 실패했다.
  기록되지 않은 원인을 추측하지 않는다. 구간 RVA와 크기는 정적 PE 및
  관찰된 메모리 매핑 범위와 대조했다.

REA 기록은 `analysis/phase4-x86-runtime/evidence.json`에 3개 있다.

| 작업 | Evidence ID |
| --- | --- |
| 제한된 코드 캡처 스크립트 로드 | `ev_bd0164a77d462397baf0c3e71d4fbddd1629ee1397dfcc80e15b32a0c714e601` |
| 세션 상태와 캡처 결과 | `ev_c00828e76be9c57579fc41f0ca74d9822884f92517ca07b24d97714153034654` |
| 메모리 매핑 메타데이터 스크립트 로드 | `ev_d2157f5fb0938bfb7e667dfee4e06500f7210ddc9e35a8e8c30d0e176cd6d88e` |

이 Evidence는 `subject: null`이며 아티팩트 신원과 OS/아키텍처를
제공하지 않는다는 자체 한계가 있다. 따라서 스크립트의 모듈 경로/주소 보고와
호스트에서 확인한 정적 파일 해시를 연결 문맥으로 사용한다.
정지 상태의 코드 스냅샷이 원본 파일의 해당 구간과 정확히 일치하는 추가
비교 근거는 있지만, 이를 전체 런타임 모듈에 대한 REA의 암호학적 신원 보장으로
확대해서 표현하지 않는다.

### 원본·실행 전·실행 후 비교

| 항목 | 값 |
| --- | --- |
| 재개 전 스냅샷 SHA-256 | `cab382c681e94d8d6ae0cc60b35f3cd23a094eba2bc0c743c881f134ee4db8d1` |
| 재개 후 2초 스냅샷 SHA-256 | `07311c8a793567d91d47f067d4d924c3fe4194f4ca1aa426e8574964e47ddd8b` |
| 8초 시점 | 2초 스냅샷과 같은 해시 |
| 원본 구간 + 0 채움 ↔ 재개 전 | **변경 0바이트**, 해시도 일치 |
| 재개 전 ↔ 재개 후 | **30,614,228바이트 변경 (93.849532%)** |
| 변경된 4 KiB 페이지 | **7,964개 / 7,964개** |
| 0이 아닌 바이트 | 13,546,928 → 29,096,990 |
| 전체 구간의 Shannon 엔트로피 | 4.291991 → 6.651646 bits/byte |

기본 주소가 동일하고 거의 모든 코드 바이트가 변경되며, 원래 0으로 채워졌던
공간에 많은 코드가 생겼다. 따라서 단순 재배치/주소 보정보다는
**실행 중 코드 압축/보호 해제가 이루어졌다는 강한 근거**다.
다만 이 비교만으로 모든 보호 계층이 사라졌다고 단정하지 않는다.

비교의 전체 변경 페이지 목록과 제한된 변경 구간 미리보기는
`analysis/phase4-x86-runtime/ida-code/prepared/comparison.json`에 있다.
재현 도구는 `tools/analyze_code_snapshot.py`이며 알려진 입력 해시를 확인한다.

### 복원된 코드의 IDA 분석

원본 PE의 첫 코드 구간을 캡처 바이트로 교체하는 **분석용 복사본**을 만들었다.
나머지 구간은 원본 파일의 정적 바이트를 유지했다. 데이터/상수 구간은 이 단계에서
실행 후 값으로 복원하지 않았으므로 관련 참조의 의미에는 한계가 있다.

IDA에 코드 시작점을 알려주기 위해 RVA `0x1000`을 분석 시드로 지정했다.
이는 **복원한 원래 진입점(OEP)이 아니다**. 실행용 PE를 만든 것이 아니다.

| 항목 | 결과 |
| --- | --- |
| 사용 엔진 | IDA Pro 9.3.260213 |
| 분석 단계 예산 | 180초, 단계 사이에서 확인하는 협력적 제한 |
| 로드·문자열 검색·저장 포함 전체 처리 | 211.5초 |
| 자동 분석 완료 여부 | **미완료**, 분석 큐가 남아 있어 함수 수는 부분 집계 |
| 인식 함수 수 전체 | 46,860개 |
| 캡처한 코드 구간 내부의 함수 수 | **46,857개** |
| 정의된 문자열 검색 수 | 122,952개 |
| x86 Hex-Rays 초기화 | 성공 |

12개 위치에서 함수의 첫 32개 명령을 표본으로 내보냈다.
별도 4개 표본을 디컴파일했고 3개에서 비어 있지 않은 의사코드를 얻었다.
부동소수점/SIMD 처리, 일반적인 C++ 객체와 문자열 처리, 예외 처리 구조가
나타난다. 앞선 보호 로더 몇 개만 보이던 상태와 달리 실질적인 네이티브 코드가
복원되었다. 표본의 기능을 카카오 로그인이나 채팅이라고 식별한 것은 아니다.

다음 파일에 실제 IDA 결과를 보관했다.

- `analysis/phase4-x86-runtime/ida-code/ida93/report.json`
- `analysis/phase4-x86-runtime/ida-code/ida93/code-inventory.json`
- `analysis/phase4-x86-runtime/ida-code/ida93/decompiled-samples.json`

원본 PE가 노출하던 import 항목 36개에는 복원 코드에서 IDA가 확인한 참조가
0개였다. 원본 보호 계층의 import 목록을 실제 앱의 Windows API 호출 목록으로
간주해서는 안 된다. 실제 IAT/읽기 전용 상수 데이터의 재구성과 함께 확인할
필요가 남아 있다.

### 아직 확인되지 않은 것

캡처한 **실행 코드 구간 안에서만** `LOGINLIST`, `CHECKIN`, `oauthToken`,
`login.json`, `registerDevice`, `ALBUS`의 정확한 ASCII 검색 결과가 각각 0개였다.
상수 문자열이 보통 코드와 다른 구간에 있다는 점을 고려하면 인증 기능 부재를
뜻하지 않는다. IDA의 기존 후보 정규식 검색도 현재 부분 이미지에서는 일치 항목이 없었다.

실제 앱 코드의 복원은 진전이지만 인증 요청의 필드·기기 등록·키 협상·채팅
세션을 식별하거나 서버에서 검증한 단계는 아니다. 현재 로그인 성공이나
일반 단체방 송수신을 보장하는 근거로 사용할 수 없다.

팀의 런타임 기록에는 소유 PID 9416을 신원 확인 후 종료했고 남은 카카오톡
프로세스가 없다고 기록되어 있다. 이 오프라인 IDA 단계에서 새 프로세스를
실행하거나 다시 연결하지 않았다.
